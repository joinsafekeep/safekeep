# Account onboarding — deployment and operations

This change adds /account/ and a Netlify Function at /api/account. The marketing site and Formspree waitlist stay independent. Authentication uses Supabase Auth with PKCE and server-managed HttpOnly, Secure, SameSite=Lax cookies. The browser never receives tokens in JSON or local storage. All account mutations require a matching Origin and JSON content type. Authenticated requests validate the user with Supabase Auth and execute database operations as that user; no service-role key is needed.

## Implemented

- Adult signup, email verification, resend, login, logout, password recovery and password change with current-password verification. Reset/change signs out all Supabase refresh sessions; existing access tokens may remain valid until expiry.
- Profiles: names, optional adult DOB, IANA timezone, adult attestation.
- Verified login email is synchronized from auth.users, not submitted claims or user metadata.
- Multiple labeled cell/home/office/other phone contacts with optional extension, E.164 validation and an explicit unverified state.
- Explicit email-practice opt-in and withdrawal, append-only consent history, quiet hours, frequency, pause. Email must match the current confirmed login address. No phone consent or sending is enabled yet. Queued practices are cancelled on withdrawal/pause; a future sender must also check current consent immediately before sending.
- Database ownership checks, strict grants and a private privileged helper with explicit auth checks. End users cannot self-verify contacts or forge consent timestamps/policy versions.

## Sign-up handoff (added October 29, 2026)

The marketing dialog no longer ends at a Stripe Payment Link. After the plan step it creates the account (password, adult attestation, Terms of Service and Privacy Policy), verifies the email with the six-digit code from the verification email (the link still works in the same browser), then sends the person to /account/ for the profile and checkout. Built to the "Sign-up" section of the MVP PRD.

- New /api/account actions: `verify_code` (email + code → session), `intent` (save a plan choice), `checkout` (returns the Stripe URL for the chosen plan with `client_reference_id` = user id and `prefilled_email`; an interim stand-in for /api/billing/checkout, same `{url}` response), `accept_policies` (re-acceptance after a version bump). `signup` now requires `terms_accepted: true` and accepts `first_name` and an `intent` object (`plan`, `billing`, `help_for`, `invitee_name`, `invitee_email`, `invitee_phone`, `lead_session_id`), validated and stored as user metadata (`safekeep_intent`, `safekeep_signup`). `state` returns `intent`, `signup`, `acceptances`, `policy_version` and `plans`.
- Terms acceptance is recorded in `policy_acceptances` (database/signup-terms.sql) the first time a verified session exists, from the timestamp, version, hashed IP and user agent captured at sign-up. `POLICY_VERSION` in account.mjs is the version string; bump it when /terms/ or /privacy/ change and the account page re-prompts.
- The adult attestation given at sign-up carries over to the profile form, so it is not asked twice.
- Metadata is still untrusted for identity. The intent only decides which plan is offered and prefills the first invite. For the acceptance record, metadata decides only whether the box was ticked at sign-up and when (bounded to the last 90 days by the RPC); the version written is the server's `POLICY_VERSION`, and `checkout` refuses until both documents are accepted at that version.
- Turnstile covers both account-creation forms: the dialog (site key on the dialog element) and the standalone form on /account/ (site key on `#signup-form`; the /account/* CSP allows challenges.cloudflare.com). The same `TURNSTILE_SECRET_KEY` enforces both.

Before deploying:

1. Apply database/signup-terms.sql to the Supabase project (table, RLS, replaced `account_action`). The function fails on `state` until it is applied.
2. In Supabase Auth email templates, add the code to the confirmation template alongside the link, for example `Your Safekeep code is {{ .Token }}` above `{{ .ConfirmationURL }}`. The dialog asks for the code; the link keeps working in the same browser.
3. In the Stripe dashboard, change each Payment Link's "After payment" redirect to `https://joinsafekeep.com/account/?checkout=success`. Until then `/?signup=complete` forwards there.
4. Optional, before public enrollment: Cloudflare Turnstile on the account-creation step. Set `TURNSTILE_SECRET_KEY` in the Functions environment and the site key in `data-turnstile-site-key` on the dialog in index.html and pricing.html (then rebuild scam-alerts). The contact step is untouched so the ads conversion is unaffected.
5. Optional: `POLICY_IP_SALT` for the IP hash on acceptance records (defaults to the app origin).
6. Funnel events: the dialog sends `signup_page_view`, `signup_form_open`, `signup_contact`, `signup_plan`, `signup_account_created` and `signup_verified` to the Google tag; create reports or conversions for them. /account/ loads no Google tag (its CSP allows only same-origin scripts), so `checkout_started`, `paid` and `first_seat` wait for the billing webhook, which can report them server-side.
7. Review Supabase Auth rate limits (sign-ups, OTP verifications, resends per hour) in the dashboard before public enrollment; `verify_code` passes Supabase's 429 through as "Please wait before trying again."
8. Still to build from the PRD: the 24h/72h "verified but never paid" reminders, the weekly cleanup of unconfirmed users older than 30 days, clearing the intent once billing has used it, and the subscription record that lets the page know a payment landed. Until then /account/ keeps "Continue to payment" available after a return from Stripe, and practice consent is hidden client-side before that return (server-side enforcement comes with the subscriptions table).

## Settings (added October 29, 2026)

Built to the "Settings" section of the MVP PRD, on top of the sign-up handoff. Migration: database/settings.sql (tests: database/settings-tests.sql, run in a transaction; both verified on a local Postgres 16 with a stand-in auth schema).

- Channels: email, text and phone are separate consents in consent_events (policy version `practice-consent-2026-10-29`). Text needs a verified cell (`kind = mobile`); phone needs any verified, unsuppressed number; email still has to match the verified login address. One number per channel is live at a time (the page withdraws the old grant before granting a new one). Turning practices on needs at least one current grant on a verified contact, on any channel.
- Phone verification: `phone_verify_start` / `phone_verify_check` call Twilio Verify (a text to a cell, an automated call that reads the code to a landline). The code is checked server-side; the database is told through `verify_phone` with an HMAC proof under `PHONE_VERIFY_SECRET`, which the RPC recomputes from `safekeep_private.secrets`. A signed-in user calling the RPC directly cannot produce the proof. `user_contacts.verification_method` records how (`otp_sms`, `otp_call`, `auth_email`, `invite_token`).
- Removing a number (`remove_phone`) keeps the row for consent history, suppresses it (`suppressed_at`, `suppression_reason = removed_by_user`), withdraws its grants and cancels its queue. The scheduler must skip suppressed contacts.
- Preferences: per-channel monthly caps (`email_cap_per_month`, `text_cap_per_month`, `call_cap_per_month`, 0–7, defaults 4/4/2), `paused_until` (a date within the next year; queued practices before it are cancelled and the scheduler resumes on its own), `alerts_opt_in`. The seven-a-month hard cap across channels and the never-two-in-a-day rule are the scheduler's to enforce.
- Family: `report_recipients` (up to five active per participant, add/remove, `unsubscribe_token_hash` filled by the report job). Who sponsors whom waits for subscription_members; the page shows a placeholder line.
- Deletion and export: `request_deletion` withdraws every grant, turns practice off, cancels the queue, removes report recipients, records the request in `account_deletions` and signs the person out everywhere; signing in within 30 days shows a banner with `cancel_deletion`. `export` returns one JSON file of everything the account holds, downloaded while signed in (a mailed copy waits for the transactional email provider). The hard delete is `netlify/functions/scheduled-cleanup.mjs`, daily, which also removes unconfirmed sign-ups older than 30 days.

Before deploying:

1. Apply database/settings.sql, then `insert into safekeep_private.secrets values ('phone_verify_proof','<value>')` with the same value as `PHONE_VERIFY_SECRET` in the Functions environment. Until both are set, verification replies "Phone verification isn’t available yet."
2. Twilio Verify: create a Verify service, set `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_VERIFY_SERVICE_SID`. Verify's own texts and calls are not A2P practice traffic, but confirm with Twilio that the service is approved for the call channel before landlines are offered.
3. Set `SUPABASE_SERVICE_ROLE_KEY` for the scheduled cleanup function only (Netlify lets a variable be scoped to functions; keep it out of any request-path function and out of client code). The job skips with a note until it is set.
4. The account page offers channel consent only after a return from Stripe or once any consent exists (page-level guard, as in the sign-up handoff); the server-side gate arrives with the subscriptions table.

## Cancellation and the subscription record (added October 29, 2026)

Built to the "Cancellation" section of the MVP PRD, with the slice of the billing layer it needs. Migration: database/billing-cancellation.sql (tests: database/billing-cancellation-tests.sql; verified locally with the earlier suites).

- `subscriptions` is fed only by Stripe webhooks (`netlify/functions/billing-webhook.mjs`, POST /api/billing/webhook): signature verified against `STRIPE_WEBHOOK_SECRET`, each event recorded once in `webhook_events`, applied with the service role. `checkout.session.completed` creates the row and the sponsor's seat from `client_reference_id` (the account's user id, which the sign-up handoff already puts on Payment Link checkouts; a pre-account session id is skipped). `customer.subscription.created/updated` keep status, price, period end and `cancel_at` current; `deleted` (or a status of canceled/unpaid/incomplete_expired) calls `end_subscription`. `invoice.payment_failed` marks past due and queues one email on the first failure; `invoice.paid` clears it; `charge.refunded` stamps `refunded_at`.
- `end_subscription(sid)` (service role only): every seat on `subscription_members` goes to `ended`, queued practices are cancelled, and sponsor and participants each get one plain email through `outbound_emails`. Annual plans are untouched until Stripe actually ends them, so access runs through the paid period.
- `is_active_participant(uid)`: the entitlement check the scheduler and the account page share (active seat on an active/trialing plan, or past due for under seven days). A user may ask only about themself.
- `leave_subscription` (account_action): a participant leaves without the sponsor cancelling; the seat frees, their queue stops, the sponsor gets an email. `my_sponsorship()` is what a participant may see of the plan: the sponsor's first name and the plan's state.
- POST /api/billing/portal (`netlify/functions/billing.mjs`): a Stripe Billing Portal session for the signed-in sponsor's customer; `/account/` shows "Manage subscription" on the plan card. The bare portal login link in the footer stays for pre-account customers.
- `outbound_emails` is drained by `netlify/functions/scheduled-email.mjs` every ten minutes through SendGrid (`SENDGRID_API_KEY`, `EMAIL_FROM`); until configured, emails wait in the table. Rows are marked sent or failed, never retried silently.
- `price_plans` maps Stripe price ids to plan, billing and seats, so a price change is a row, not a deploy. Unknown prices get one seat.

Before deploying:

1. Apply database/billing-cancellation.sql, then insert the six live prices into `price_plans` (price id, plan, billing, seats 1/2/4).
2. In Stripe, add a webhook endpoint for `https://joinsafekeep.com/api/billing/webhook` with the events listed above and set `STRIPE_WEBHOOK_SECRET`; set `STRIPE_SECRET_KEY` (used by the webhook to read a subscription after checkout and by the portal function). Configure the Billing Portal in Stripe (allow cancel and card update; plan changes can stay off until the invitations phase handles seat downgrades).
3. `SENDGRID_API_KEY` and `EMAIL_FROM` for the sender function, scoped to functions. `SUPABASE_SERVICE_ROLE_KEY` is now used by three scheduled/webhook functions and still by no request-path function.
4. Existing subscribers who paid through a Payment Link before accounts: their events carry a session id, not a user id, so they are skipped; attach them by inserting a `subscriptions` row and sponsor seat by hand (the admin tool is a later phase).

## Server-created checkout (added October 29, 2026)

The `checkout` action now creates a Stripe Checkout Session when `STRIPE_SECRET_KEY` is set: the price comes from `price_plans` (readable by signed-in users through database/billing-checkout.sql), `client_reference_id` and `subscription_data.metadata.user_id` carry the account, a returning sponsor reuses the Stripe customer from their latest plan (a row only the webhook writes), and success returns to `/account/?checkout=success&session_id=…`, where the page polls for up to 40 seconds until the webhook has created the plan. If there is no key, no price row, or Stripe refuses, it falls back to the Payment Link, still keyed to the account. Stripe creates the customer during checkout, so no request-path code ever decides which Stripe customer an account maps to.

- The restricted key needs **Checkout Sessions: Write** in addition to Subscriptions: Read and Customer Portal: Write.
- `STRIPE_AUTOMATIC_TAX=true` turns on Stripe Tax for new sessions (Stripe Tax must be set up first). `STRIPE_TERMS_AT_CHECKOUT=true` requires the Terms checkbox on Stripe's page (needs a Terms URL in Stripe's public business details); the webhook records it as a `checkout` acceptance.
- Twilio: `TWILIO_API_KEY_SID` + `TWILIO_API_KEY_SECRET` (a restricted key) are preferred over `TWILIO_ACCOUNT_SID` + `TWILIO_AUTH_TOKEN`.
- Admin attach for pre-account Payment Link customers is not built: the six live prices had no active subscriptions when this shipped, so there is no one to attach.

## Invitations (added October 29, 2026)

Built to "Gifting to a family member" in the MVP PRD. Migration: database/invitations.sql (tests: database/invitations-tests.sql).

- A sponsor invites from the Your seats section of /account/ (first name, email, optional phone used only to prefill, optional note). The database writes the invitation and queues the email; the link is `<app_origin>/invite/?t=<token>`, where `app_origin` comes from `safekeep_private.secrets`, never from a request. Seats in use = participants plus invitations still out; a full plan refuses another.
- The invited person opens /invite/, sees who sent it and the note, and either creates an account (email fixed to the invited address, 6-digit code like any sign-up), signs in, or says no thanks without an account. **Acceptance requires a signed-in user whose verified login email equals the invited address**, so the token only identifies the invitation: a sponsor who sees their own outgoing link still cannot accept for someone else, and no service-role key is needed on the request path. This replaces the PRD's "the invite token stands in for email verification", which would have needed the service role on a public page and let anyone holding the link create the account.
- Resend rotates the token (the old link stops working) and restarts 14 days. Cancel revokes. A daily job (`scheduled-invitations.mjs`) reminds on day 3 and day 10 and, on day 14, lapses the invitation and tells the sponsor once. Declining tells the sponsor kindly. When a plan ends, pending invitations are revoked.
- A sponsor who said the plan is for themself gets a participant seat at checkout; "Add myself" does the same later if a seat is free. `subscription_members` is now one row per role; `is_active_participant` counts participant seats only. One live participant seat per person (a unique index).
- Sponsors see, through `sponsor_seats()`, each participant's first name, status and the names of the channels they turned on, never an address, number or schedule. Removing a participant stops their practice and tells them; their account stays.

Before deploying: apply database/invitations.sql, then `insert into safekeep_private.secrets values ('app_origin','https://joinsafekeep.com')`. The invite email waits for the email sender (SendGrid).

## Email practice (added October 29, 2026)

Built to phase 4 of the MVP PRD ("Email practice, end to end"), with the parts of "Practice scam engine", "Delivering practice scams" and "Coaching" it needs. Migration: database/practice.sql (tests: database/practice-tests.sql). Seed: database/practice-seed.sql, generated from content/practice-library/email.json by `npm run practice:seed`.

- Library. Versions now carry tells (each quoting the message word for word), channel_variant (for email: from-name and the sender's local part), brand_mode, expires_at, next steps, the one question, and a context link. The seed is 20 email scenarios across the PRD's categories at 8 easy, 8 medium and 4 hard, and goes in as drafts. The build fails if a tell doesn't appear in its message, a real brand is named, or coaching uses "fail", "fell for" or "victim".
- Review queue at /admin/ (and /api/admin). Admins are rows in `admin_users`, checked inside the database. Approve publishes; edit makes a new draft and the published version stays live until that draft is approved, then it retires; reject retires the draft with a note. Nothing reaches published without a click. Deliveries are listed with a Suppress button.
- Planning (`plan_practices`, every ten minutes from `scheduled-practice.mjs`): one practice waiting at a time per participant; a channel with a current grant on a verified, unsuppressed contact; a published version they haven't had in 180 days; the first three at difficulty 1 or 2, then one step up after two spotted in a row and one step down after a practice opportunity; categories they recently clicked weighted up. It keeps to the weekly cap, each channel's monthly cap, seven a month in all, never two on the same local day, and a random time outside quiet hours in their time zone.
- The pre-send check (`send_blocker`, run by `claim_due_practices` right before each send): active participant seat, practice on, not paused, no deletion pending, contact verified and unsuppressed, latest consent for that contact and channel is a grant, version still published, monthly cap and one-a-day still hold. A failure cancels the row with the reason. A row due inside quiet hours is moved to the next window instead.
- Sending: SendGrid from `<from_local>@PRACTICE_EMAIL_DOMAIN`, with click and open tracking off (no pixels). The function refuses to start unless the practice domain differs from the EMAIL_FROM domain, PRACTICE_POSTAL_ADDRESS is set and PRACTICE_SENDING=on. Every email has a footer with the stop link and the postal address, plus List-Unsubscribe and one-click headers. **"Safekeep practice message" shows on every practice email for now** (PRACTICE_FOOTER=always), because the PRD leaves open whether harder ones may go without it until counsel has read the CAN-SPAM rules; set PRACTICE_FOOTER=easy_only to show it on difficulty 1 and 2 only. A temporary send failure retries once, half an hour later; a second failure stops there.
- Coaching at /p/<token> (on PRACTICE_LINK_ORIGIN, for example practice.joinsafekeep.com, added to the same Netlify site). The token is random, stored only as a hash and works for 30 days. The page opens with a POST, so mail scanners that fetch links don't count as a click. First open records link_clicked and "practice opportunity"; every open records coaching_viewed; the question records debrief_completed (first answer kept, right or wrong). Sharing sends a family member their own link (up to three), which shows the page without the outcome and can't stop practice or answer. The page sends no referrer.
- Stopping: the footer link and the one-click header both withdraw consent for that address and cancel anything planned to it. A spam complaint does the same.
- "Was this Safekeep?" on /account/: the participant says email, text or call and roughly when. If we sent one, it's marked spotted and the short congratulatory page opens; otherwise they're told plainly it wasn't us. The history lists a practice only once its outcome is known, so it can't be used to check a message still in its window. Past coaching reopens from the history after the link expires. Sponsors see none of this.
- Bounces (`/api/practice/events`, SendGrid's signed Event Webhook): a hard bounce or a dropped address suppresses the contact, cancels what's planned to it, and emails the participant (and a gifted seat's sponsor) that email practice has paused until they update it. 72 hours after a send with nothing seen, the result becomes "ignored it". A version retires when its expires_at passes or when fewer than 5% of 20 or more sends led to a click.

Before deploying: apply database/practice.sql, then database/practice-seed.sql, then add yourself as an admin with `insert into public.admin_users(user_id) select id from auth.users where email='<your login>'` and review the 20 drafts at /admin/. Set PRACTICE_EMAIL_DOMAIN (with SPF, DKIM and DMARC through SendGrid domain authentication), PRACTICE_LINK_ORIGIN, PRACTICE_POSTAL_ADDRESS and SENDGRID_WEBHOOK_PUBLIC_KEY; point SendGrid's signed Event Webhook at /api/practice/events with delivered, bounce, dropped and spam report events; then set PRACTICE_SENDING=on.

## Required before real-user launch

1. In Netlify, review and deploy the GitHub branch. netlify.toml builds only public assets into dist; server code, SQL, tests, dependencies and docs are not published as static files. Use Node 22.
2. Configure APP_ORIGIN in Netlify's Functions environment to the exact canonical origin (e.g. https://joinsafekeep.com), with no trailing slash. Optional overrides are SUPABASE_URL and SUPABASE_PUBLISHABLE_KEY; current project publishable defaults are built in and are not secrets. Do not configure a service-role key. Production cookies are always Secure. Local development can use APP_ORIGIN=http://localhost:8888 and COOKIE_SECURE=false. Preview deployments need their own exact origin and redirect allowlist entry; don't set a production APP_ORIGIN in a preview.
3. In Supabase Auth URL Configuration, set the site URL and allow the exact redirects https://joinsafekeep.com/account/ and https://joinsafekeep.com/account/?flow=recovery (replace origin for an approved preview). Use standard confirmation/reset templates containing .ConfirmationURL so PKCE codes return to this handler. Verification/reset links must be opened in the same browser where requested. Request a new email if the browser changes or a newer request replaced the verifier cookie. GET merely displays the confirmation form; POST consumes the code. No automatic code exchange by a link scanner.
4. Configure production SMTP and a verified sender domain. Supabase's default email service is restricted and not appropriate for public onboarding. An existing Twilio account can supply SMS later; email needs its own configured sender (e.g. SendGrid SMTP if already available). Do not paste provider credentials into chat, GitHub, or public environment variables.
5. Set the Supabase password policy to at least 12 characters (the application also enforces 12–128), enable leaked-password protection where available, review Auth rate limits, and add bot protection before public enrollment. Configure equivalent edge/IP controls on the account function; server-to-server Auth calls can share network rate limits. Avoid request-body logging and analytics on /account/.
6. Run a real mailbox acceptance test on the deployment: signup → email verification → profile → add phone → consent → preferences → sign out → sign in → reset email → set password → old password rejected → new password accepted. Check code replay and expiry, resend behavior, two-account isolation, mobile form layout and error messaging. Do not mark these passed from mocked endpoint tests.

MFA enrollment, self-service email editing, invitations, live messaging and server-created checkout are not built. Do not advertise these as implemented. Production personal-data collection should wait for retention/deletion handling and the launch checks above.
